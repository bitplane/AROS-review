# AROS network-stack source review

Source snapshot: `282a0454356dc2b9554ab023997d7f7ca24fc03e`. This is a source-only candidate list, not runtime reproduction. Paths and line numbers below are relative to the repository. The primary built stack is `workbench/network/stacks/AROSTCP/bsdsocket` (see its `mmakefile.src`); `arch/all-mingw32/bsdsocket` is a separate Windows-hosted variant (see its `mmakefile.src`). The initial scan sampled the socket API and resolver, buffer/socket core, IPv4/TCP/UDP, IPv6/ICMPv6/neighbor discovery and fragmentation, routing, SANA-II interface glue, timers and build selection. The file-by-file audit is tracked in [AROS-network-coverage.md](AROS-network-coverage.md). Network device drivers, user applications, and wireless managers are separate regions.

**Status: file-by-file audit underway.** The coverage ledger currently contains 247 unique file rows: 1 reviewed, 6 with full-body review but broader callers pending, 13 with body inspections awaiting broader caller checks, and 227 explicitly unreviewed. The Windows-hosted `accept.c` body is now checked against its selected module manifest; its stub behavior is already covered by candidate 8. Findings remain source-only candidates; the audit is incomplete and may omit defects.

## Candidate bugs

1. **IPv6 fragment reassembly accepts overlapping fragments (high confidence).** `workbench/network/stacks/AROSTCP/bsdsocket/netinet6/ip6_input.c:221-240` sorts fragments by starting offset without rejecting overlap or duplicate offsets; the completion walk at `:243-259` only checks whether the next fragment starts at `next_expected`, and updates that value from the current fragment. A sequence with a duplicate or overlapping fragment can leave a queue that never completes; more seriously, a last fragment followed by another contiguous fragment can satisfy `have_last` and append data past the declared end. Reject overlaps and require the last fragment to be terminal. Affected: AROSTCP IPv6 input.

2. **A failed fragment-descriptor allocation leaves an empty IPv6 reassembly queue (high confidence).** `workbench/network/stacks/AROSTCP/bsdsocket/netinet6/ip6_input.c:177-207` creates and links a new queue before allocating its first descriptor. If the allocation at `:209-215` fails, the function frees the mbuf but does not unlink the new queue or decrement `ip6q_nfragpackets`. Repeated allocation failures retain empty queues until timeout, consume queue slots, and can evict valid reassemblies. Affected: AROSTCP IPv6 under memory pressure.

3. **IPv6 reassembly rewrites the wrong next-header field after extension headers (high confidence).** The queue remembers `fh->ip6f_nxt` at `workbench/network/stacks/AROSTCP/bsdsocket/netinet6/ip6_input.c:194-199`; completion unconditionally sets the *base* IPv6 header's `ip6_nxt` to it at `:309-312`. If a Hop-by-Hop or Destination Options header preceded the Fragment header, this discards that header from the protocol chain while its bytes remain in the packet. Record and replace the preceding header's next-header byte instead. Affected: IPv6 fragments with an extension header before Fragment.

4. **IPv6 destination matching admits addresses that are not all-nodes multicast (high confidence).** `workbench/network/stacks/AROSTCP/bsdsocket/netinet6/ip6_input.c:559-563` recognizes `ff02::1` using only byte 0, byte 1 and byte 15, without checking bytes 2–14 are zero. Packets for unrelated `ff02::...:1` multicast groups are delivered locally. Compare the entire 128-bit address. Affected: AROSTCP IPv6 multicast input.

5. **`getifaddrs()` silently truncates interface enumeration (high confidence).** The default non-`NET_RT_IFLIST` path uses a fixed 1024-byte IPv4 buffer at `workbench/network/stacks/AROSTCP/bsdsocket/api/getifaddrs.c:112-124,233-259` and a 32-entry IPv6 buffer at `:261-279`, with no retry or truncation indication. `in6_ifconf` stops filling when space runs out at `workbench/network/stacks/AROSTCP/bsdsocket/netinet6/in6.c:629-648`, returning success and only bytes written. Hosts with more addresses than fit get a successful but incomplete interface list. Affected: AROSTCP interface APIs and callers such as Miami `if_nameindex`.

6. **`if_nameindex()` cannot enumerate interfaces through the normal `getifaddrs()` path (high confidence).** `workbench/network/stacks/AROSTCP/bsdsocket/api/if_nameindex.c:105-145` counts only `AF_LINK` addresses. The default `getifaddrs()` implementation at `workbench/network/stacks/AROSTCP/bsdsocket/api/getifaddrs.c:420-475` emits IPv4 and IPv6 socket addresses but no `AF_LINK` record. Thus it returns just the terminator on that build path even when interfaces exist; `if_indextoname()` in `api/if_indextoname.c:78-86` likewise returns ENXIO. Affected: normal builds without `NET_RT_IFLIST`.

7. **IPv6 addresses returned by `getifaddrs()` have zero interface flags (medium confidence).** `workbench/network/stacks/AROSTCP/bsdsocket/api/getifaddrs.c:448-472` fills IPv6 entries with `ifa_flags = 0` and null netmask, rather than the actual interface flags and prefix. Callers checking `IFF_UP` or using the prefix may skip working IPv6 addresses or infer wrong network boundaries. Affected: IPv6 address enumeration.

8. **Windows-hosted BSD socket operations report success without doing work (high confidence; hosted variant only).** `arch/all-mingw32/bsdsocket/mmakefile.src:5-54` includes calls whose implementations are placeholders. `bind.c:47-50`, `connect.c:47-50`, `listen.c:44-47`, `accept.c:47-50`, `send.c:46-49`, `recv.c:46-49`, `recvfrom.c:52-56`, `sendmsg.c:47-50`, `recvmsg.c:47-50`, and `waitselect.c:50-53` return zero without calling Winsock or setting a failure. Programs may believe a bind/connect/send succeeded, or interpret zero as EOF, while no network operation occurred. Related placeholder entry points should be audited as one implementation gap. Affected: `arch/all-mingw32` bsdsocket library; not the AROSTCP stack.

9. **Windows-hosted blocking `sendto()` does not complete after `EWOULDBLOCK` (high confidence; hosted variant only).** `arch/all-mingw32/bsdsocket/sendto.c:75-91` explicitly identifies synchronous AROS sockets backed by asynchronous Winsock sockets, but the completion branch is empty. A blocking caller receives `-1`/`EWOULDBLOCK` instead of waiting and retrying. Affected: Windows-hosted socket library when Winsock send would block.

10. **SANA-II error formatter can index one past the generic error table (high confidence).** `workbench/network/stacks/AROSTCP/bsdsocket/net/sana2perror.c:48-56` rejects a negative `io_Error` only when `-err > io_nerr`, then indexes `io_errlist[-err]`. `io_nerr` is the number of entries (see `api/amiga_errlists.c:206` and the `>= io_nerr` check in `api/amiga_generic2.c:789`), so `io_Error == -io_nerr` reads one pointer past the table. A driver returning that value can cause an invalid string read while logging an error. Use `>=`.

11. **Packet-filter callbacks run while holding the hook-list semaphore (medium-high confidence).** `workbench/network/stacks/AROSTCP/bsdsocket/net/pfil.c:112-141` holds a shared `pfil_list_lock` while invoking each third-party hook. `api/miami_api.c:257-275` takes the same semaphore exclusively in `MiamiPFRemoveHook`. A hook that unregisters itself (or registers another hook) before returning can deadlock on a shared-to-exclusive acquisition; a stalled hook also blocks every list writer. This code is enabled by `bsdsocket/conf.h:327`. Copy or pin the hook list, then invoke callbacks without holding the list lock.

12. **Windows-hosted socket initialization leaks its resolver IRQ on failure (high confidence; hosted variant only).** `arch/all-mingw32/bsdsocket/host_socket.c:52-78` allocates `SocketIRQ` and then `ResolverIRQ`. If `CreateEvent` or `CreateThread` fails after the second allocation, the cleanup calls `KrnFreeSystemIRQ` only for `SocketIRQ`. The resolver slot stays allocated, so repeated failed initialization consumes the finite host IRQ slots (`arch/all-mingw32/kernel/host_intr.c:379-403`) and leaves its event unavailable for reuse. Free `ResolverIRQ` on every failure after its allocation. Affected: Windows-hosted socket startup under host resource failure.

13. **Windows-hosted socket initialization leaks a successful Winsock startup when later resource setup fails (conditional host resource leak; high source confidence).** `sock_init` calls `WSAStartup` and returns immediately only when that call itself fails (`arch/all-mingw32/bsdsocket/host_socket.c:44-50`). Every later failure path—either system IRQ allocation, resolver event creation, or resolver thread creation—returns `NULL` without calling `WSACleanup` (`:52-81`). The selected `bsdsocket_Init` caller returns failure when `sock_init` returns `NULL` (`arch/all-mingw32/bsdsocket/bsdsocket_init.c:61-66`), and its expunge cleanup invokes `sock_shutdown` only when a controller was returned (`:79-91`); therefore the failed initialization cannot balance that Winsock reference. Repeated attempts after host-resource failures can retain Winsock startup references. Route all post-`WSAStartup` failures through cleanup that calls `WSACleanup`. No failure was induced. Source-only.

15. **AROSTCP can send a log reply through the SysLog port after it has been freed (conditional teardown race).** `workbench/network/stacks/AROSTCP/bsdsocket/kern/amiga_log.c:599-600,672-673` reads the shared `ExtLogPort` pointer and then calls `PutMsg()` without synchronization that pins the port. The in-tree SysLog utility shuts down by calling `RemPort(Port)`, then `SetSysLogPort()` (which replaces `ExtLogPort` with `FindPort("SysLog")`, now NULL), drains the queue, and calls `DeleteMsgPort(Port)` (`workbench/network/stacks/AROSTCP/syslog/main.c:397-405`; `bsdsocket/api/miami_api.c:1100-1114`). NETTRACE can read the old non-NULL pointer before this sequence and be delayed until after `DeleteMsgPort()`, then enqueue to freed port memory. Synchronize pointer acquisition/use with SysLog teardown, or use a handshake that waits for in-flight sends before deleting the port. This requires an AROSTCP log send overlapping the normal SysLog utility shutdown; no interleaving was run. Source-only.

14. **Windows-hosted socket shutdown frees the resolver IRQ before its worker has stopped (conditional stale IRQ delivery; high source confidence for missing synchronization).** The resolver thread can finish a normal wake by clearing `Command` and calling `KrnCauseSystemIRQ(ResolverIRQ)` (`arch/all-mingw32/bsdsocket/host_socket.c:21-36`). `sock_shutdown` writes the shutdown command, signals the event, and immediately frees both IRQs without joining or otherwise waiting for the resolver thread (`:84-97`). If shutdown overlaps a worker iteration that has already passed its event wait and is about to cause the resolver IRQ, that call can occur after the IRQ has been freed or reassigned. Keep the IRQ allocated until the worker is confirmed stopped, with synchronization around the in-flight callback. No concurrent shutdown was induced. Source-only.

## NW15

**The MinGW32 `Inet_NtoA()` call reverses the pool and memory arguments to `FreeVecPooled()`.** On the first successful conversion, `taskBase->inaddr` is still zero because the per-task base is allocated with `MEMF_CLEAR` (`arch/all-mingw32/bsdsocket/bsdsocket_open.c:72-73,93`; `rom/exec/makelibrary.c:104-106`). The function calls `FreeVecPooled(taskBase->inaddr, taskBase->pool)` before storing the newly copied result (`arch/all-mingw32/bsdsocket/inet_ntoa.c:55-63`). `FreeVecPooled()` returns only when its second argument (`memory`) is NULL, then immediately passes the first argument to `IsManagedMem()`, which dereferences it as a `MemHeader` (`rom/exec/freevecpooled.c:53-62`; `compiler/include/exec/memheaderext.h:57-60`). The reversed call supplies a null pool header and a nonnull real pool as `memory`, so the first successful `inet_ntoa()` call reaches a null-header dereference. Swap the arguments and keep the existing buffer as the memory argument. **Affected configuration and trigger:** MinGW32 builds selecting `arch/all-mingw32/bsdsocket/inet_ntoa.c`, when `inet_ntoa()` succeeds for a task's first conversion. **Consequence:** the conversion faults in `FreeVecPooled()` before returning its new string. **Confidence:** high for the argument order, cleared initial field, and unconditional null-header dereference; no Windows call was run. Source-only.

## NW16

**MinGW32 protocol-entry cleanup frees pooled storage through the wrong APIs and reverses `FreeVecPooled()` arguments.** `CopyStringArray()` allocates its pointer array with `AllocVecPooled(pool, ...)`, but `FreeStringArray()` releases it with `FreeVec(src)` (`arch/all-mingw32/bsdsocket/netdb_util.c:31-42,59-67`). `FreeVec()` subtracts its size prefix and passes the resulting interior address to `FreeMem()`, which is not the paired pool deallocator (`rom/exec/freevec.c:51-61`). The same cleanup then uses `FreeVecPooled(entry->p_name, pool)`, reversing the documented `(poolHeader, memory)` arguments (`netdb_util.c:98-105`; implementation at `rom/exec/freevecpooled.c:53-71`). The selected `getprotobyname()` caller reaches this cleanup when replacing a previous successful result (`arch/all-mingw32/bsdsocket/getprotobyname.c:73-77`) and on `CopyProtoEntry()` failure (`netdb_util.c:91-93`); `FreeStringArray()` is reached whenever the entry has its allocated alias vector, including an empty alias vector. Use `FreeVecPooled(pool, src)` for the vector and `FreeVecPooled(pool, entry->p_name)` for the name. **Affected configuration and trigger:** MinGW32 builds selecting this resolver code, on a repeated successful `getprotobyname()` call or any cleanup of a partially or fully copied protocol entry. **Consequence:** the mismatched vector release can pass a pool suballocation to the system allocator, and the reversed call treats the string address as a pool header and the actual pool address as memory; cleanup can fault or corrupt allocator state instead of releasing the old result. **Confidence:** high for both allocator mismatches and selected cleanup callers; exact failure depends on pool contents and allocator validation. No resolver call or free was run. Source-only.

## NW17

**A failed protocol-name allocation sends an uninitialized alias pointer into cleanup.** `CopyProtoEntry()` obtains `entry` with `AllocPooled()` from the task's `MEMF_ANY` pool, assigns `entry->p_name`, but assigns `entry->p_aliases` only inside `if (entry->p_name)` (`arch/all-mingw32/bsdsocket/netdb_util.c:69-92`; pool creation at `arch/all-mingw32/bsdsocket/bsdsocket_open.c:66`). If the name allocation fails, it still calls `FreeProtoEntry(entry, pool)`, which tests the uninitialized `entry->p_aliases` field and may pass its garbage value to `FreeStringArray()` (`netdb_util.c:98-105`). Initialize both pointer fields before any fallible copy or make the cleanup path aware of which fields were initialized. **Affected configuration and trigger:** MinGW32 builds selecting the protocol resolver when `AllocVecPooled()` fails while copying `wsentry->p_name` after the `protoent` allocation succeeded. **Consequence:** cleanup may read an arbitrary alias pointer and walk/free memory through it, turning an ordinary allocation failure into a fault or pool corruption. **Confidence:** high that the field is uninitialized on this branch and consumed by cleanup; the resulting behavior depends on the reused pool bytes. No allocation failure was induced. Source-only.

## NW18

**A partial alias-copy failure is returned as a successful but incomplete protocol entry.** `CopyStringArray()` breaks when any element's `CopyString()` fails, writes a NULL terminator at that index, and returns the non-NULL array (`arch/all-mingw32/bsdsocket/netdb_util.c:31-56`). `CopyProtoEntry()` treats any non-NULL result as complete and returns the `protoent` (`:81-88`), so allocation pressure after one or more alias copies silently omits the remaining aliases while `getprotobyname()` reports success (`arch/all-mingw32/bsdsocket/getprotobyname.c:58-64,73-82`). Free the already-copied strings and array and propagate failure instead of returning a truncated alias list. **Affected configuration and trigger:** MinGW32 protocol resolver when allocating an alias string fails while later alias entries remain to be copied. **Consequence:** callers receive an apparently valid `protoent` with an incomplete alias list, which can make protocol-name lookup by alias fail or return inconsistent metadata. **Confidence:** high for the break/return flow and success handling; no allocation failure or resolver call was induced. Source-only.

## NW20

**MinGW32 `bsdsocket.library` reports a successful per-task open when its descriptor table allocation fails.** `BSDSocket_OpenLib()` creates the per-task pool and `TaskBase`, then calls `SetDTableSize(FD_SETSIZE, tb)` without checking its result before adding the task base to the AVL tree and incrementing both open counts (`arch/all-mingw32/bsdsocket/bsdsocket_open.c:66-107`). `SetDTableSize()` returns `ENOMEM` when `AllocPooled()` cannot allocate the pointer table, and leaves the zero-initialized `dTable` and `dTableSize` unchanged (`bsdsocket_util.c:37-65`; `rom/exec/makelibrary.c:108-130`). Exec's pool allocator can fail while obtaining the first real puddle after `CreatePool()` has allocated only the pool handle (`rom/exec/createpool.c:113-129`; `rom/exec/memory.c:1150-1155`). Because Open still returns the non-NULL `TaskBase`, `OpenLibrary()` reports success. The first `socket()` call scans zero descriptor slots, sets `EMFILE`, and returns `-1` (`bsdsocket_util.c:68-80`; `socket.c:50-59`). Later opens from the same task reuse the already-published task base and do not retry table initialization (`bsdsocket_open.c:58-64`). Propagate the `SetDTableSize()` failure and remove/free the partially initialized task base before returning NULL.

**Affected configuration and trigger:** the MinGW32 hosted `bsdsocket.library` target (`arch/all-mingw32/bsdsocket/bsdsocket.conf:1-7`; module selection in `mmakefile.src:53-57`), when the per-task pool cannot grow to satisfy its initial descriptor-table allocation during `OpenLibrary()`. **Consequence:** Open reports success for a task whose socket table has zero entries; socket creation fails with `EMFILE` until that task base is closed and a later open successfully recreates it. `SocketBaseTagList()` is an unimplemented stub in this target and provides no table-resize recovery (`socketbasetaglist.c:43-46`). **Confidence:** high for the ignored allocation result and zero-table socket failure; the trigger requires pool-growth failure. No allocation failure or socket operation was induced. Source-only.
